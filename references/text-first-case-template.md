# 文字优先的拟人化界面验证案例模板

没有图时直接填写此模板；有图时将截图作为对应步骤的参考或证据。每个案例只验证一个清楚的业务结果。

```markdown
# <案例 ID>：<业务结果，例如“已支付订单可完成部分退款”>

## 测试上下文

- 风险级别：P0 / P1 / P2
- 需求、缺陷或接口资料：<链接/编号>
- 执行环境：local / test / staging
- 测试角色：<角色名称；不记录密码>
- 测试数据：<fixture@版本，或已脱敏快照的版本>
- 业务时间与时区：<固定值或比较规则>
- 允许副作用与清理：<会创建什么，如何回收>

## 前置条件

1. <例如“存在一笔实付 100 元、未退款的测试订单”>。
2. <例如“退款服务使用测试支付渠道，异步结果最长 30 秒”>。

## 测试人员操作脚本

### S01：进入待验证对象

- 入口：从 `<系统首页/URL>` 进入，依次打开 `<菜单 A> → <菜单 B>`；或直接访问 `<URL 模式>`。
- 看见：页面标题为 `<标题>`；搜索区域有 `<字段>`；列表显示 `<前置数据识别方式>`。
- 操作：在 `<搜索字段>` 输入 `<订单号变量>`，点击 `<查询>`。
- 当场预期：列表出现一条与该订单匹配的记录，状态为 `<状态>`。
- 复核位置：点击该记录的 `<详情>`，进入订单详情页。
- 证据：截取列表筛选结果和详情页标题；订单号可脱敏。

### S02：执行业务动作

- 当前页面：订单详情页，确认实付金额显示 `<100>`，累计退款显示 `<0>`。
- 操作：点击可见名称为 `<退款>` 的按钮；在 `<退款金额>` 输入 `30`；在 `<退款原因>` 选择 `<测试原因>`；点击 `<确认退款>`。
- 当场预期：页面展示 `<退款申请成功>` 或进入 `<退款处理中>`；记录本次请求的追踪标识（如可见）。
- 异步处理：刷新或重新打开详情页，最多等待 `<30 秒>` 直到状态到达 `<成功终态>`；未到达即失败，不用固定 sleep 代替。
- 证据：操作前后关键区域截图，以及脱敏的请求 ID/响应摘要。

### S03：跨页面核验用户可见结果

- 入口：从当前详情页打开 `<退款记录>`；若需返回列表，明确点击 `<返回订单列表>` 后的筛选条件。
- 看见：存在一条本次退款记录，金额为 `30`，状态为 `<成功终态>`。
- 操作：再次打开订单详情，核对累计退款额。
- 页面预期：累计退款额从 `0` 变为 `30`，订单状态仍为 `<已支付>`。
- 证据：退款记录与订单详情截图。

### S04：接口与数据核验（仅在已授权时执行）

- 接口预期：`<退款接口>` 返回 `<HTTP 状态/业务码>`；金额为 `30`；响应业务键与订单详情中的记录关联。
- 数据预期：累计退款额的前后差值为 `30`；累计退款额不大于实付额；本次退款记录关联该订单。
- 不变量：相同幂等键再次提交不产生第二条退款业务效果。
- 动态字段：订单号、退款单号、UUID、时间戳不写死；校验格式、关联关系、顺序或时间窗口。

## 反向与边界验证

- <例如“输入 101 元时，不允许提交，并展示明确错误”>。
- <例如“无退款权限的角色无法看见或无法使用退款操作”>。
- <例如“网络重试或重复点击不产生重复退款”>。

## 通过标准

- 所有标记为硬性断言的 UI、接口和数据规则通过。
- 证据完整，隔离测试数据已清理或保留可追踪标识。
- 未授权或未执行的检查必须明确列出，不能算通过。
```

## 写作检查

每一步至少包含“入口、观察、操作、页面预期、复核位置”。接口或数据校验要写清要比较什么，而不是只写“检查数据库”。当需求没有给出页面名称、控件名称或正确结果时，保留 `待确认`，不要让 AI 编造。
