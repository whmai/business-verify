# 从需求生成指导测试验证集

在开始实现前使用此模板。它的作用是把需求翻译成 AI 与测试人员都可以执行的验收门禁，而不是写一份抽象的“测试点清单”。

```markdown
# <功能名称>：指导测试验证集

## 输入与边界

- 需求来源及版本：<链接、编号或文本摘要>
- 被测范围：<页面、接口、角色、状态变更>
- 明确不在本次范围：<内容>
- 已知待确认项：<需求未说明且不能合理推断的控件、口径、权限或异常行为>

## 需求—验证案例映射

| 需求 ID | 需求的可观察结果 | 覆盖案例 | 验证层级 | 风险 |
| --- | --- | --- | --- | --- |
| R-01 | <例如“用户可发起部分退款”> | BV-01 | UI + API + 数据 | P0 |
| R-02 | <例如“退款不能超过实付额”> | BV-02 | UI + API + 数据 | P0 |

## BV-01：<正向业务路径，描述业务结果>

### 前置条件

- 测试环境：<local/test/staging>；账号角色：<角色>。
- 数据：<fixture@版本；例如已支付 100 元、无退款的订单>。
- 业务时间与外部依赖：<逻辑时间、异步最长等待、测试替身>。

### 拟人化操作与验证

1. **进入对象。** 从 `<首页/URL>` 打开 `<菜单路径>`，到达 `<页面名称>`。确认页面出现 `<标题/查询控件>`。
2. **定位数据。** 在 `<字段>` 输入 `<测试订单标识>`，点击 `<查询>`。确认列表只出现或包含目标订单，且当前状态为 `<已支付>`。
3. **进入详情。** 点击该订单的 `<详情>`。确认实付金额为 `100`、累计退款额为 `0`。
4. **执行操作。** 点击 `<退款>`，在 `<退款金额>` 输入 `30`，选择 `<退款原因>`，点击 `<确认>`。记录页面显示的请求追踪信息（如有）。
5. **观察即时结果。** 确认看到 `<成功提示/处理中状态>`；若异步，刷新或重新进入详情，最长等待 `<30 秒>` 直到 `<成功终态>`。
6. **跨页面复核。** 打开 `<退款记录>`，确认新增一笔金额为 `30` 的记录；返回订单详情，确认累计退款额变为 `30`，订单状态仍为 `<已支付>`。
7. **核对后台结果（获授权时）。** 退款接口返回 `<成功业务码>`；退款记录关联该订单；累计退款额的前后差为 `30`，且不超过实付额。

### 通过标准与证据

- UI、接口、数据硬性断言全部通过；保存脱敏截图、请求 ID 和查询结果摘要。
- 订单号、退款单号、UUID、时间戳为动态字段，只检查格式、关联关系和前后差值。

## BV-02：<边界或反向路径>

1. 重复使用 BV-01 的前置状态。
2. 从订单详情打开退款，输入 `101`。
3. 点击确认；确认页面阻止提交并显示明确错误。
4. 若接口被调用，确认它返回对应的业务错误；确认订单累计退款额和退款记录均未变化。

## 覆盖缺口

- <例如“需求未定义退款处理中是否允许取消，因此不能定义断言，需业务确认”>。

## 自测门禁

- 实现前：BV-01/BV-02 的相关验证应至少有一项可观察地失败或尚未具备实现。
- 实现后：逐项执行，报告每个需求 ID 与案例 ID 的通过、失败或未执行原因。
- 禁止仅凭成功弹窗、HTTP 200 或 Agent 的语言判断宣布通过。
- 硬性案例失败时：保存证据，判断是实现、测试/夹具、环境还是需求问题；属于实现缺陷时自行修正，并从干净夹具回测失败案例、受影响案例和全部 P0 案例。
- 持续“诊断 → 修正 → 回测”，直至全部硬性案例通过。需求歧义、缺少权限/环境或超出授权范围时不得伪造通过；明确报告阻塞并继续完成不受影响的案例。
- 最终交付仅在全部硬性案例通过后允许；报告须包含需求—案例结果、修复轮次和最终回测证据。存在未执行、失败或阻塞的硬性案例时，结论必须为未完成。
```

## 最低覆盖基线

对每个需求，至少考虑：主成功路径、输入校验/业务边界、权限或可见性（如果涉及角色）、重复提交/幂等性（如果会产生写入）、异步失败或外部依赖失败（如果存在）、以及数据前后关系。并非每项都必须适用；不适用时写出理由。
