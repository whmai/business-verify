# 后端设计与可维护性门禁

这是一项验证集门禁，不是“写完再顺手重构”。后端功能实现前先用代码图谱、调用链或代码搜索了解已有模块、接口、领域类型、错误处理、日志与文件放置惯例；每个新增或修改的后端模块都在验证集中记录结论与证据。

## 先参照项目已有实现

1. 先找到相近业务功能，检查它所在目录、分层、文件命名、模块接口、调用链、错误处理和日志格式；项目已有惯例优先于个人偏好。
2. 寻找同一业务动作、相近参数、相同外部依赖或相同状态规则的现有实现；列出候选项、调用者和复用结论。
3. 新文件必须放在与其职责一致、且与项目既有相似代码一致的位置。不能因为方便就在 Controller、工具包或随机目录塞入领域逻辑；若既有结构不适用，说明原因和替代位置。

## 复用、模块与模式

- 仅在语义、事务、权限、错误语义和性能约束一致时复用或通过小而内聚的参数扩展。避免万能方法、参数/布尔标志膨胀、分支堆砌和重复实现。
- 确有新变化点时，设计深模块：让调用者面对小而清楚的接口，把编排、校验、重试和细节放在实现内。仅当变化或替换真实存在时引入 seam、Strategy、Factory、Adapter 或 Template Method；不要为了模式而模式。
- 领域规则不应散落在 Controller/UI 或多个调用点；不要跨层复制校验、映射、查询或异常转换。公共接口说明输入、错误、幂等性、顺序和性能约束。

## 必要注释与运维日志

- 注释解释“为什么”：业务不变量、取舍、兼容性、并发/事务陷阱或代码看不出的外部约束；不逐行复述显而易见代码。公共接口和复杂决策按项目规范补充文档。
- 对关键写入、异步任务、外部调用和故障路径使用项目既有格式的结构化日志、指标或追踪，关联请求/追踪 ID、必要时脱敏的业务键、结果/错误类别和耗时。
- 不记录密码、令牌、完整个人信息、敏感请求体；不在循环中刷噪声日志；不以日志替代错误处理或测试。日志级别与采样遵循项目惯例。

## 工具、常量与业务选项

- 发现可跨调用方复用、无状态且与具体业务无关的纯逻辑时，先检索项目已有公共工具模块；没有合适能力才在项目约定的公共工具位置新增，并为其公开接口、边界和测试负责。不要把高度业务化、只有一个调用方或会引入不合理依赖的方法过早塞进全局 `Utils`。
- 重复出现且语义稳定的固定值应使用有业务名称的常量，不要散落魔法字符串、数字、路径或错误码。部署环境可变值、密钥和运营配置应走项目配置机制，而不是编译期常量。
- 同一领域的常量、类型或选项应遵循项目惯例集中在同一模块/文件或内聚命名空间，避免新建“万能常量文件”；引用方直接使用命名符号。
- 对封闭且稳定的多选业务状态/类型/策略使用枚举或等价的受限领域类型，业务代码直接引用枚举值而非字面量。选项若由数据库、租户或运营配置动态扩展，则使用受校验的配置/注册表，不强行建枚举。
- 变更枚举、常量或公共工具时，验证序列化/反序列化、数据库或 API 兼容性、默认处理和未知值处理；不要仅因代码能编译就视为安全。

## 通过标准

| 检查 | 通过标准 |
| --- | --- |
| 项目惯例与代码放置 | 已比对相近实现；文件位置、分层、命名和职责有依据。 |
| 复用审计 | 已列出现有候选、调用链与采用/拒绝理由；无无故重复业务实现。 |
| 模块/接口 | 接口小而内聚，真实复杂性在实现内；新增抽象/模式有明确变化点和测试收益。 |
| 注释 | 非显而易见的业务或技术决策已解释；无重复代码的噪声注释。 |
| 可观测性 | 关键成功、失败和外部调用可诊断，关联字段充分且敏感数据被排除。 |
| 工具、常量与选项 | 通用无状态逻辑落在正确公共工具模块；稳定值无魔法字面量；封闭业务选项以枚举/受限类型直接引用，并完成兼容性检查。 |
| 工程门禁 | 项目既有格式化、静态检查、类型检查、构建、测试及审查通过。 |

如果项目没有相关规范，记录缺口和建议的最小约定；不要把个人风格冒充为项目标准。发现重复、浅接口、错误放置、缺失必要注释/可观测性或无收益模式时，应像功能失败一样修正并回测，之后才可交付。
